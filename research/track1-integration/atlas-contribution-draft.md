# Draft: ATLAS mitigation update -- routing-header/body consistency for chained agent components

Status: internal draft, not submitted. No new technique proposed; no ATLAS ID requested.

## 1. Proposed contribution

An update to two existing ATLAS mitigations' guidance text, naming routing-header/request-body
consistency checking as a concrete instance of validation they already cover in general terms --
supported by audit-telemetry guidance and a controlled integration exercise showing the behavior
end-to-end against a real, pinned SDK. No new technique, tactic, or mitigation is proposed; no
ATLAS ID is requested.

**Candidate placements** (current official wording, verified against the ATLAS mitigations
data -- not assumed from memory):

- **AML.M0033, "Input and Output Validation for AI Agent Components."** Current text (verified,
  not assumed): "Implement validation on inputs and outputs for the tools and data sources used by
  AI agents. Validation includes enforcing a common data format, schema validation... Validation
  should be performed external to the AI agent." A routing-layer field (an MCP `Mcp-Method`/
  `Mcp-Name` header, or an equivalent signal in another agent protocol) disagreeing with the
  request body it accompanies is a data-format consistency problem between two representations of
  the same tool/resource invocation -- a specific case of "enforcing a common data format" at a
  component boundary, external to the agent, exactly as M0033 already scopes it.
- **AML.M0024, "AI Telemetry Logging."** Current text: "Implement logging of inputs and outputs of
  deployed AI models... implement logging of the intermediate steps of agentic actions and
  decisions, data access and tool use... Monitoring logs can help to detect security threats." The
  addition below is narrower: the logged validation decision should be correlated with what a
  downstream component actually did, using correlation context the logging layer itself
  generates -- not a client-supplied identifier -- so a rejected attempt is not conflated with an
  executed one in the audit trail.

## 2. Demonstrated behavior

Five bounded cases, run against the real, pinned MCP SDK (`@modelcontextprotocol/{client,server,
node}@2.0.0`) plus one clearly-labeled, non-SDK, deliberately unprotected stand-in used only for
case 3.

| # | Case | Server execution | Client response validation | Authorization outcome |
|---|------|------|------|------|
| 1 | Matching header/body (standard enforcement) | Executed; real server's own SEP-2243 check active | Accepted | N/A -- no conflict |
| 2 | Conflicting header/body (standard enforcement) | **Rejected** by the real server's own check (`-32020` HeaderMismatch) | Rejected (server error) | N/A -- rejected before execution |
| 3 | Same conflict, **explicitly weakened lab-only mode** | **Executed** (proven independently, not by response alone -- see below) | Rejected (unrelated client-side envelope-shape error) | `outcome_unknown` -- no authorization evidence collected |
| 4 | Encoded/decoded identity, matching (standard enforcement) | Executed; no false-positive mismatch | Accepted | N/A -- no conflict |
| 5 | Concurrent requests, reused JSON-RPC id (standard enforcement) | Both executed independently, no cross-contamination | Both accepted | N/A -- no conflict |

Case 3 is the only case using the weakened stand-in: a hand-written `node:http` process, not the
SDK, used because the real server has no documented option to disable its own check. Its execution
was proven by three independent, mutually-corroborating sources keyed to one gateway-issued
correlation ID: the raw HTTP exchange, an out-of-band execution log written as a side effect of
handling the request, and a persisted state-change (a read counter, 0->1) -- not response status
alone. Execution is not labeled unknown; only whether it was *authorized* is (no separate
authorization evidence exists in this lab).

## 3. Proposed mitigation text (addition)

> Where a routing-layer signal (e.g., a header) and the request body it accompanies each carry a
> value identifying the same tool, resource, or task, validate that the two values agree before
> routing or executing the request -- applying the protocol's required decoding first (e.g.,
> reversing any header encoding convention) so equivalent representations of the same identity are
> not flagged as conflicting. Reject requests where the values disagree rather than routing on one
> and executing on the other. Record the validation decision (agreement, conflict, or
> missing/malformed) in telemetry, and correlate it with independent evidence of what a downstream
> component actually did, using request context generated by a trustworthy component in the
> request path -- not a client-supplied or otherwise attacker-influenceable identifier. The
> resulting record should distinguish a rejected attempt from one that reached execution.

## 5. Limitations

- Controlled, local-only lab using two fictional resources; not a discovered product vulnerability
  and not a proven unauthorized-access exploit.
- Case 3 used an explicitly weakened, non-SDK, clearly-labeled stand-in -- the real SDK's own
  check was never bypassed, patched, or disabled; it has no such option.
- Requires custom telemetry instrumentation (`lib/audit.js`) to produce the events described; no
  product ships this by default.
- Correlation uses a gateway-issued request-instance ID, not one generated by the MCP server SDK
  itself -- verified not overridable by client input (see `REPORT.md`), but a lab-specific
  mechanism, not a standardized field.
- No claim of a new ATLAS technique; this proposes wording additions to two existing mitigations.
- The project's native-KQL testing (a local Kusto emulator, under `evidence/native-execution/`) is
  unrelated to this exercise. This exercise's detector evaluation used a JS reference-oracle model
  (`tests/detections/oracle.js`), not a native query engine; Splunk was not involved or restarted.
