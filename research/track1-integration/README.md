# Track 1 integration lab (research)

Local-only integration lab producing real, request-processing-derived evidence for Track 1
(Task Routing Header/Body Desynchronization), as research toward a potential MITRE ATLAS
contribution. Not a published detection artifact; does not change `detections/`, Track 2, or
Track 3.

**Not independent SDK validation.** The real, pinned `@modelcontextprotocol/{client,server,node}@2.0.0`
line is used for the client and the honest server. One component (`weakened-server.js`) is a
hand-written, clearly-labeled non-SDK stand-in used only for bounded case 3, because the real
server SDK has no documented way to disable its own header/body check -- see its file header for
the verification that led to that conclusion.

## Topology

```
client-runner.js  --(HTTP, X-Lab-Case header)-->  gateway.js  --(HTTP)-->  server.js (real SDK)
                                                                       \-->  weakened-server.js (lab-only, case 3)
```

`gateway.js` is project-authored lab infrastructure, not part of any SDK. It is the only place a
header/body mismatch is introduced -- the real client SDK always sends body-consistent headers
itself (confirmed by reading its shipped source; see `gateway.js`'s header comment).

## Requirements

- The documented `resources/read` method is used as the identity-bearing request, not `tasks/get`:
  the installed SDK's SEP-2663 Tasks extension has no runtime (see `../../docs/sdk-discrepancy.md`).
  `resources/read`'s `params.uri` goes through the identical Mcp-Name cross-check mechanism.
- The client must pin the modern protocol era explicitly (`versionNegotiation: { mode: { pin:
  '2026-07-28' } }`) -- its own default is `'legacy'`, under which Mcp-Method/Mcp-Name are never
  sent at all. See `client-runner.js` and `server.js` for the two further wrinkles this uncovered
  (the installed package's own `SUPPORTED_PROTOCOL_VERSIONS` excludes 2026-07-28 by default, and
  the modern `server/discover` pre-probe only works when serving with `createMcpHandler`, not a
  manually-paired persistent `McpServer` + per-request transport).

## Reproduction

```
cd research/track1-integration
npm install
bash run-lab.sh
```

This starts all three local HTTP processes on 127.0.0.1 (ports 4000/4001/4002, overridable via
`TRACK1_LAB_GATEWAY_PORT`/`TRACK1_LAB_SERVER_PORT`/`TRACK1_LAB_WEAKENED_PORT`), runs the real
client through all 5 bounded cases, derives telemetry-contract events, evaluates the existing
Track 1 detector, and stops the processes. See `REPORT.md` for the actual results and
`evidence/` for the raw records the report is drawn from.

## Files

- `server.js` -- real MCP server (`@modelcontextprotocol/server@2.0.0`).
- `weakened-server.js` -- **not an MCP SDK**; lab-only stand-in for case 3 only.
- `gateway.js` -- project-authored intermediary; the only header/body mismatch injection point.
- `client-runner.js` -- real MCP client (`@modelcontextprotocol/client@2.0.0`) running all 5 cases.
- `lib/correlate.js` -- gateway-generated request-instance correlation (not JSON-RPC id).
- `lib/audit.js` -- derives `mcp.request.validation` telemetry events from raw evidence.
- `evaluate-detector.js` -- runs the existing `tests/detections/oracle.js` Track 1 oracle (a JS
  model, not a query engine) against the derived events.
- `evidence/` -- generated by `run-lab.sh`; not hand-written.
- `REPORT.md` -- results, separating demonstrated behavior from assumptions.
