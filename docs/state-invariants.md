# State Invariants: MCP Tasks, Authorization, and Long-Lived Subscriptions

Companion to `docs/threat-model.md`. Each row is a single, testable invariant. "Normative"
invariants are directly required by the current MCP specification (`2026-07-28`) or SEP-2663;
invariants marked **[overlay]** are detection-design constructs this project layers on top of
the protocol because the protocol itself does not define an equivalent field or event (see
threat-model.md §16–17 for the full normative-vs-assumption discussion). No detection logic is
implied by this table — it records what "normal" and "violation" mean at the state level only.

| # | Invariant | Normal | Violation | Detection Track | Required Telemetry |
|---|---|---|---|---|---|
| 1 | `Mcp-Method` header equals the JSON-RPC `method` field | Header value and body `method` are byte-identical, on any request where the negotiated protocol version requires the header | Header and body `method` differ under a protocol version that mandates the header (server should reject with `HeaderMismatch`/`-32020`, but the disagreement itself is the signal of interest, e.g. for intermediary-vs-server desync) | Track 1 | Raw `Mcp-Method` header value; JSON-RPC `method`; negotiated `MCP-Protocol-Version`; server error code/status if rejected |
| 2 | `Mcp-Name` header equals the request's identity field | For `tools/call`/`resources/read`/`prompts/get`: header equals `params.name`/`params.uri`. For `tasks/get`/`tasks/update`/`tasks/cancel`: header equals `params.taskId` (decoded from Base64-sentinel form if used) | Header names/identifies a different tool, resource URI, or `taskId` than the body | Track 1 | Raw `Mcp-Name` header (decoded), `params.name`/`params.uri`/`params.taskId`, method, `HeaderMismatch` presence |
| 3 | Missing header vs. conflicting header are distinct conditions | Header absent **and** negotiated protocol version predates the header requirement (e.g., `2025-03-26` semantics, no `MCP-Protocol-Version` sent) | Header **present** but its value conflicts with the body, under a protocol version that requires the header — this is a real desync, not a compatibility gap | Track 1 | Negotiated protocol version; presence/absence of each standard header; header value vs. body value when present |
| 4 | Caller is authorized for the referenced task | Authenticated principal issuing `tasks/get`/`tasks/update`/`tasks/cancel` matches (or is explicitly granted against) the server-side authorization context bound to that `taskId` | A different, non-granted principal issues a syntactically valid request against someone else's `taskId` | Track 2 | Authenticated principal/subject per request; `taskId`; server-side authorization-context owner/grant list; server allow/deny decision (not just the wire response code — see #5) |
| 5 | Task not-found and not-authorized are not assumed to be wire-distinguishable **[overlay: detection must compensate]** | SEP-2663 normatively requires `-32602` only for an invalid/nonexistent `taskId`; it does not specify a code for "exists but unauthorized," so a `-32602` response is consistent with either case and must not be assumed to mean "doesn't exist" | N/A — this is not itself a violation; it is an unresolved protocol ambiguity (not a confirmed implementation behavior) that limits what client-visible telemetry alone can prove for invariant #4 | Track 2 | Server-internal authorization-check log distinct from the client-visible `-32602`; without it, Track 2 cannot be reliably detected from wire data alone |
| 6 | Task ID unguessability | `taskId` values are high-entropy, server-generated, non-sequential | Observed `taskId` values are sequential, low-entropy, or otherwise predictable/enumerable | Track 2 (risk indicator, not proof of a violation by itself) | Distribution/format of issued `taskId` values over time |
| 7 | Terminal task states are final | Once a task reaches `completed`/`failed`/`cancelled`, subsequent `tasks/update`/`tasks/cancel` against it are rejected by the server | A `tasks/update` or `tasks/cancel` is accepted (state-mutating) against a task already in a terminal state | Track 2 (lifecycle-integrity boundary) | Task status timeline per `taskId`; accept/reject outcome of each `tasks/update`/`tasks/cancel` |
| 8 | Subscription acknowledgment precedes notifications | `notifications/subscriptions/acknowledged` (carrying `subscriptionId`) is the first message observed for a given `subscriptionId`; no other notification for that ID precedes it | A notification carrying a given `subscriptionId` is observed before that ID's acknowledgment | Track 1 / Track 3 boundary | Ordered notification stream per `subscriptionId` with timestamps |
| 9 | Subscription delivery matches the acknowledged filter | Every notification delivered on a `subscriptionId` is one of the types/URIs/`taskId`s present in that subscription's acknowledged filter | A notification of a type, resource URI, or `taskId` outside the acknowledged filter is delivered on that `subscriptionId` | Track 1 / Track 3 boundary | Acknowledged filter contents (`toolsListChanged`, `resourceSubscriptions`, `taskIds`, etc.) vs. each delivered notification's type/URI/taskId |
| 10 | Active subscription stays consistent with current authorization **[overlay: no protocol-defined transition]** | Every notification delivered on an active `subscriptions/listen` stream is delivered while the authorization that justified opening it is still valid, or within an explicit, deployment-defined grace period after a change. Note: for ordinary resource/list-changed notifications this is a change/activity-metadata signal (they carry no resource contents — see threat-model.md §11), not a claim that resource contents themselves are exposed | A notification (`notifications/resources/updated`, `notifications/tasks`, list-changed) is delivered strictly after the justifying authorization was revoked/expired/downgraded, with no applicable grace period. (Whether a given notification also inlines protected content, as `notifications/tasks` can via `CompletedTask.result`, is tracked separately — see row 11a) | Track 3 | Token/grant validity window; authorization-change event timestamp (from the authorization server or policy system); `subscriptionId`; per-notification delivery timestamp; configured grace-period policy (if any) |
| 11 | Revocation propagation delay is bounded and expected | A short gap between an authorization-server revocation event and the MCP server's next authorization check, consistent with the deployment's known token-introspection/cache TTL | A gap between revocation and continued delivery that exceeds the deployment's documented propagation/grace-period bound | Track 3 | Same as #10, plus the deployment's configured introspection/cache TTL or grace-period bound, so "expected delay" can be distinguished from "drift" |
| 11a | `notifications/tasks` inlined-result exposure **[overlay: unvalidated hypothesis, not an established invariant]** | Not yet applicable — this row records an open question, not a confirmed behavior | A drifted `notifications/tasks` delivery whose `DetailedTask` body inlines a `CompletedTask.result` after authorization has lapsed would be a direct content disclosure, distinct from the metadata-only exposure in row 10 | Track 3 (flagged sub-case) | Requires experimental validation against a running Tasks-extension implementation before being treated as confirmed; not assumed true in this document |
| 12 | Output/token/size signals are enrichment only | Any output-schema size, item count, or token usage value, on its own, produces no Track 1/2/3 classification | N/A by design — this invariant is never "violated" in the sense of triggering detection; the violation this row guards against is a *detection design* mistake (treating size/tokens as a primary signal) | Applies to all tracks (explicitly a non-primary-signal guard) | Output payload size, item count, input/output token usage — recorded as context alongside a genuine Track 1/2/3 finding, never as the sole trigger |
