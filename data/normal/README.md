# Block 3 — Normal MCP Telemetry Corpus

This is the reproducible, negative-test corpus for all three locked detection tracks
(`docs/threat-model.md`). Every event here is expected to produce **zero** Track 1/2/3 alerts.
Block 3 is not attack simulation — no Task-A/Task-B mismatches, unauthorized principals,
post-revocation notifications, or malformed routing appear anywhere in this directory. Those
are explicitly reserved for Block 4.

## How this corpus was produced — read this before trusting any file here as "real traffic"

**None of this corpus was captured from a live official MCP SDK server/client exchange** — but
this is narrower than it may first sound. The official TypeScript SDK has two current lines:
the legacy **v1** (`@modelcontextprotocol/sdk`, latest `1.30.0`), which targets protocol
`2025-11-25`, and the stable **v2** (`@modelcontextprotocol/client` + `@modelcontextprotocol/server`,
latest `2.0.0`), which **does** implement MCP `2026-07-28` core — including genuine, runtime
`Mcp-Method`/`Mcp-Name` header validation and a genuine `subscriptions/listen`. What v2 does
*not* yet implement is the current shape of the **SEP-2663 Tasks extension**: it still ships
only the pre-SEP-2663 `tasks/get`/`tasks/result`/`tasks/list`/`tasks/cancel` core-protocol
methods, has no `tasks/update`, and its task-status notification type is marked directly in its
own shipped source as `@deprecated 2025-11-25 wire vocabulary with no SDK runtime`. Full
verification details and citations: `docs/sdk-discrepancy.md`.

Because 11 of these 13 scenarios are task-centric, every event in this corpus is still produced
by **`tools/harness/generate.js`**, a small, deterministic Node.js program that:
- implements the *actual* validation/state-machine logic documented and cited in Block 1
  (`tools/harness/lib/protocol.js` computes Track 1 verdicts from raw header/body inputs — it
  does not accept a hand-typed verdict), so results are harness-computed, not hand-labeled;
- tracks real task/subscription state transitions in-memory rather than typing each event's
  `previous_state` by hand;
- uses a fixed logical clock and no `Math.random()`, so re-running it reproduces the corpus
  byte-for-byte.

Every scenario below is labeled in `manifest.jsonl` with a `provenance` field, using one of
three values:
- **`official_sdk_v2`** — not currently used by any scenario in this corpus. Reserved for a
  future pass: N8 (the one scenario with no task involved) is a real candidate, since v2's
  `subscriptions/listen` is genuinely functional — see `docs/sdk-discrepancy.md` for why that
  swap wasn't made in this pass (it would require standing up real client/server processes and
  a wire-capture pipeline, trading away this corpus's current byte-for-byte determinism).
- **`project_reference_harness`** — generated by the mechanism above. This is the honest label
  for the deterministic, spec-conformant code path used everywhere Tasks-extension mechanics
  are involved (11 of 13 scenarios) and, for consistency, everywhere else in this pass too. It
  is not an official SDK and is never represented as one.
- **`synthetic_enrichment`** — used only for N11: the `gen_ai.usage.*` token counts are
  illustrative fabricated numbers because no LLM was invoked (Block 3 explicitly forbids
  adding an LLM solely to make this scenario possible). Everything else in that event (task
  lifecycle, authorization, routing) is still harness-computed, not fabricated — only the two
  token-count values are synthetic.

**Test environment assumptions:** Windows 11, Git Bash + PowerShell available, network access
available (used only for the one-time npm registry/version check). Python was not available in
this environment (`python`/`pip` unresolved) — this is why the generator and test harness are
both Node.js rather than Python; no functional requirement drove that choice.

## Regenerating the corpus

```
cd tools/harness
node generate.js
```

No `npm install` is required — the harness uses only Node's built-in `crypto`, `fs`, and `path`
modules. Re-running always overwrites `data/normal/*.jsonl` and `manifest.jsonl` with an
identical byte-for-byte result (fixed clock, fixed identifiers, fixed HMAC key).

## Running the validation tests

```
node --test tests/normal/*.test.js
```

(from the repository root; requires Node ≥ 18's built-in test runner, verified on `v24.18.0`).
21 tests, covering Track 1/2/3 invariants plus the enrichment/privacy rules below.

Ground truth for every scenario (`scenario_id`, `expected_security_outcome`,
`expected_detection_track_1/2/3`, `notes`) lives in **`manifest.jsonl`**, one JSON object per
scenario — kept separate from the telemetry `*.jsonl` files so those stay strictly conformant
to the Block 2 schema (no test-harness-only fields mixed into real event records).

For all 13 scenarios: `expected_detection_track_1 = expected_detection_track_2 =
expected_detection_track_3 = false`. N11/N12/N13 use a `benign_*` qualifier on
`expected_security_outcome` (never bare `"benign"`) to flag that they are diagnostic/
compatibility/synthetic cases rather than plain positive-path traffic, per the Block 3
ground-truth labeling rule — the track booleans are still `false` for all of them.

## Expected event sequences (event.name order per scenario)

- **N1:** `mcp.task.state` → `mcp.request.received` → `mcp.request.validation` →
  `mcp.task.authorization` → `mcp.response`
- **N2:** `mcp.task.state`(working) → `mcp.task.state`(input_required) →
  `mcp.request.received` → `mcp.request.validation` → `mcp.task.authorization` →
  `mcp.response` → `mcp.task.state`(working)
- **N3:** `mcp.task.state`(working) → `mcp.request.received` → `mcp.request.validation` →
  `mcp.task.authorization` → `mcp.task.state`(cancelled) → `mcp.response`
- **N4:** `mcp.task.state`(working) → 6 × [`mcp.request.received` → `mcp.request.validation` →
  `mcp.task.authorization` → `mcp.response`] → `mcp.task.state`(completed)
- **N5:** four independent `mcp.task.state` chains (see manifest notes for exact transitions)
- **N6:** `mcp.task.state`(working) → 2 × [full request/validation/authorization/response],
  one per principal
- **N7:** 3 × [`mcp.request.received` → `mcp.request.validation` → `mcp.task.authorization`
  (deny) → `mcp.response` (`-32602`)]
- **N8:** `mcp.subscription.open` → `.acknowledged` → `.notification` ×2 → `.close`
- **N9:** `mcp.subscription.open` → `.acknowledged` → `.notification` →
  `.authorization_change` → `.close`
- **N10 / N11:** `mcp.task.state`(working) → request/validation/authorization →
  `mcp.task.state`(completed, with size/token enrichment) → `mcp.response`
- **N12:** same shape as N1, with several optional fields genuinely absent throughout
- **N13:** `mcp.request.received` → `mcp.request.validation` → `mcp.response` (no
  `mcp.task.*`/`mcp.authz.*` events — this is a plain `tools/call`, not a task operation)

## Known SDK/harness limitations

- No scenario exercises `stdio` transport (`mcp.transport = "stdio"`); everything here is
  `streamable-http`. `stdio` has no headers to compare at all, which is a legitimate but
  untested-here compatibility path.
- N9 demonstrates only the `timing_confidence = authoritative` (i.e., `effective_at` known)
  variant of a clean post-revocation closure. A `detected_only` variant (only `detected_at`
  known — the more common real-world case per `telemetry/correlation.md`) is schema-supported
  and covered structurally by `tests/normal/track3.test.js`'s guard test, but is not yet
  generated as its own manifest scenario.
- See `docs/sdk-discrepancy.md` for the precise SEP-2663 Tasks-extension gap in the official
  v2 SDK this harness exists to work around (v2's core `2026-07-28` support is otherwise
  genuine), and what to re-check before Block 4.

## A note on the `mcp.authz.reason` value used for "task does not exist" (N7c)

Block 2's `mcp.authz.reason` enum has no dedicated "not found" value. N7's third case (a
`taskId` that does not correspond to any known task) uses `context_unbound` — read as "there is
no authorization context to bind to, because there is no task" — rather than inventing a new
enum value or misusing `unknown`. This is a documentation choice within the existing locked
enum, not a change to Block 2, and is called out here for transparency.
