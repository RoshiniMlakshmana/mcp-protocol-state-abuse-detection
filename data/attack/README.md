# Block 4 — Controlled Attack/Control Corpus

Reproducible, local, deterministic telemetry proving each of the three locked detection tracks
(`docs/threat-model.md`) fires exactly when its specific invariant is violated, and does not
fire otherwise. Directly comparable to the Block 3 normal corpus: same event schema, same
hashing scheme (`security.hash.key_id = block3-test-key-v1`), same real (recomputed, not
hand-labeled) Track 1 validation logic from `tools/harness/lib/protocol.js`, generated by the
same class of harness (`tools/harness/generate_attacks.js`, added alongside — not replacing —
`generate.js`).

**Safety:** every scenario here is synthetic, local, and self-contained. No external MCP
server, real credential, stolen token, or third-party system is targeted or referenced anywhere
in this corpus or its generator.

## How to regenerate / test

```
cd tools/harness && node generate_attacks.js      # writes data/attack/**/*.jsonl + manifest.jsonl
node --test tests/attack/*.test.js                # from the repo root; 34 tests
node --test tests/normal/*.test.js tests/attack/*.test.js   # both corpora together; 56 tests
```

Regeneration is byte-for-byte deterministic (fixed logical clocks per scenario, fixed
identifiers, fixed HMAC test key — same one Block 3 uses).

## Per-scenario detail

### Track 1 — Task Routing Desynchronization

**A1/A2/A3 — task identity mismatch on `tasks/get`/`tasks/update`/`tasks/cancel`.**
`Mcp-Name` identifies Task-A; `params.taskId` in the body identifies Task-B; `Mcp-Method`
matches the body method. **Invariant violated:** routing header task identity must equal
request body task identity (`docs/state-invariants.md` row 2). **Why security-relevant:** an
intermediary or gateway that routes/authorizes on the header alone would act on Task-A while
the server executing the body acts on Task-B — exactly the "different components, different
sources of truth" risk the `2026-07-28` spec's own header-validation rule exists to close
(`docs/threat-model.md` §9). **Proof:** `mcp.validation.name.result = conflict` while
`mcp.validation.method.result = match`; no `mcp.task.authorization` event exists at all,
because a `HeaderMismatch` (`-32020`) rejects the request at validation, before any
authorization check runs — this is also why Track 2 stays false here (there's no authorization
evidence at all, not an affirmative "allow"). **Detection track:** 1 only. **Class:**
project-specific detection test of a real, spec-cited protocol mechanic — not a claim of a
distinct named attack.

**A4 — method mismatch.** `Mcp-Method: tasks/get` while the JSON-RPC body method is
`tasks/cancel`; the referenced task identity matches on both sides. **Invariant violated:**
routing header method must equal request body method (row 1). **Proof:**
`mcp.validation.method.result = conflict`, `mcp.validation.name.result = match` — the mirror
image of A1-A3, isolating the other half of Track 1's routing check.

**A5 — dual mismatch.** Both method and identity disagree simultaneously. **Proof:** both
`mcp.validation.method.result` and `mcp.validation.name.result` independently record
`conflict` — the Block 2 schema's decision to keep these as two separate fields (rather than
one collapsed flag) is exactly what lets both findings survive in the same record without one
overwriting the other.

**A6 — missing-header compatibility control.** A client negotiates protocol version
`2025-03-26`, which predates `Mcp-Method`/`Mcp-Name` entirely (SEP-2243, introduced
`2026-07-28`). **Not an attack.** Both fields resolve to `version_incompatible` (not
`missing`), rolling up to `mcp.validation.result = valid`. This exists purely to prove
false-positive separation: any later detection logic that keys on "header absent/conflicting"
must not fire on this fixture the way it fires on A1-A5. **Important scoping note:** a header
*missing under a version that does require it* (`2026-07-28`) would itself be a genuine Track 1
violation per the locked model (the real MCP spec's own `HeaderMismatch` conditions include a
missing required header) — that distinct case is not fabricated here as a "benign missing
header" case; it is implicitly covered by treating any non-`version_incompatible` `missing`
result as bad (`tools/harness/lib/protocol.js`'s `BAD_RESULTS` set), consistent with A1-A5's
`conflict` results.

### Track 2 — Cross-Principal Task Authorization Violation

**A7/A8/A9 — unauthorized `tasks/get`/`tasks/update`/`tasks/cancel`.** Task-123 is authorized
for Alice; Bob, a different authenticated principal, attempts the operation with **perfectly
matching routing** (`Mcp-Name` = body `taskId`, `Mcp-Method` = body method). **Invariant
violated:** the caller must be authorized for the referenced task/operation (row 4). **Why
security-relevant, and not novel:** cross-principal task-ID abuse is already anticipated by
SEP-2663 itself, which treats task IDs as bearer-token-like credentials and mandates a
per-request authorization check specifically because of this risk (`docs/threat-model.md`
§10). This project does not claim to have discovered this attack class — it operationalizes an
already-known, spec-acknowledged risk into concrete, testable telemetry. **Proof:**
`mcp.authz.decision = deny`, `mcp.authz.reason = principal_mismatch`, alongside a routing
validation that independently recomputes to `valid`. **Deliberately NOT the proof:** the
response's `rpc.status_code` (`-32602`) — that code is wire-identical to an ordinary
task-not-found error (Block 1 §10), so these fixtures exist specifically to demonstrate that
Track 2 must never be inferred from it alone.

**A10 — stolen valid handle.** Mechanically identical to A7 (perfectly-routed, denied
`tasks/get`), but the attacker is "Mallory" rather than "Bob," modeling an external party who
obtained Task-123's real identifier some other way (leakage, logs, a shared screen) rather than
a known coworker overstepping. The telemetry shape is intentionally the same as A7 — that is
the point: **Track 2 cannot and should not distinguish attacker narratives; it can only see
server-side authorization evidence, which looks the same regardless of how the attacker
obtained the identifier.** This is why Track 1 alone (which would find nothing wrong here — the
routing is perfectly valid) is insufficient on its own to catch this class of abuse.

**A11 — legitimate shared-access control.** Deliberately **not duplicated** here. Block 3's
`N6` (`data/normal/authorized_shared_access.jsonl`) already represents an explicit
multi-principal grant cleanly (Alice owner, Bob explicitly granted, both `allow` with
distinguishable `mcp.authz.reason` values), so this manifest entry points directly at that file
rather than fabricating new semantics for no added evidence. `tests/attack/*.test.js` reads it
via this pointer to confirm Block 4's test suite validates cross-block consistency directly,
not just its own newly-generated files.

### Track 3 — Long-Lived Subscription Authorization Drift

**A12 — revocation drift (the canonical case).** Timeline exactly as specified: open 10:01 →
active 10:02 → revoked (`effective_at` = `detected_at` = 10:10, `timing_confidence` =
`authoritative`) → notification 10:11 → eventual disconnect 10:20. **Invariant violated:** an
active subscription must remain consistent with current authorization state (row 10) — a
notification was delivered a full minute after an authoritative revocation, with no closure in
between. Per Block 1 §11, this is scoped as a change/activity-signal exposure
(`notifications/resources/updated` carries only a URI), not an assumed content disclosure.

**A13 — token expiry drift.** No push revocation ever occurs — the grant simply expires
(`mcp.authz.valid_until` = 09:30). A notification at 09:45 (15 minutes past expiry) with the
stream still active. **Why this matters:** most real OAuth deployments have no push-based
revocation feed at all (`telemetry/schema.md` §5, "fields that cannot realistically be
collected"); Track 3 must therefore be able to detect drift from `mcp.authz.valid_until` alone,
with zero reliance on an `mcp.subscription.authorization_change` event ever existing.

**A14 — delayed revocation observation.** `effective_at` = 10:10, `detected_at` = 10:14,
notification = 10:12. The notification is recorded in the raw event stream *before* the
`authorization_change` event even arrives (which only happens at 10:14) — but that event's
authoritative `effective_at` retroactively proves 10:12 was already a violation. This is
precisely the scenario the Block 2 patch separated `effective_at` from `detected_at` to handle:
a detection approach using only "have we detected a change recently" would need the change
event to exist *before* it could ever flag 10:12, and would need to reason backward in time
once it arrives — using `effective_at` directly sidesteps that.

### Controls

**A15 — detected-only timing (ambiguous, not a true positive).** Same `detected_at` (10:14) and
notification (10:12) shape as A14, but with **no** trustworthy `effective_at` anywhere
(`timing_confidence = detected_only`). Because the notification precedes `detected_at`, and no
authoritative boundary exists, the true revocation moment is unknown — it could be before or
after 10:12. Per the locked timing-confidence model, this must not be asserted as a
high-confidence violation. `expected_detection_track_3 = false`, `expected_confidence = low`,
`expected_security_outcome = ambiguous_insufficient_confidence`. Comparing A14 and A15
side-by-side isolates `effective_at` presence as the one variable that flips the correct
verdict.

**A16 — correct stream termination (positive control).** Same revocation shape as A12/A14
(authoritative `effective_at`), but the application does the right thing: it closes the stream
(`close.reason = server_forced_authz`) 500ms after revocation, before any further notification.
`expected_detection_track_3 = false`. Kept in Block 4 rather than Block 3 specifically so it
sits directly alongside the true-positive fixtures with the same timeline shape, for contrast.

### Experimental

**A-EXP1 — task notification with inlined result (experimental, not required for Track 3).** A
`notifications/tasks` notification carrying `mcp.subscription.notification.contains_inline_result
= true`, delivered after an authoritative revocation. This tests the separately-flagged,
**experimentally unvalidated** hypothesis from `docs/threat-model.md` §11/§17 (row 11a) that a
drifted Tasks-extension notification could leak actual result content rather than mere
change-metadata. **Explicitly generated only by the project reference harness.** Per
`docs/sdk-discrepancy.md`, no current official SDK (v1 or v2) implements a live
`notifications/tasks` runtime — the v2 line's task-status notification type is marked directly
in its own shipped source as `@deprecated ... no SDK runtime` and uses the wrong (pre-SEP-2663)
method name. This scenario does not establish that current SDKs behave this way; it exists so a
later block *could* test the hypothesis if the harness's shape is ever validated against a real
implementation. Track 3's core proof does not depend on it (A12/A13/A14 already suffice).

### Combined

**A17 — routing mismatch then unauthorized access, same attacker session.** Mallory first
attempts a routing-mismatched `tasks/get` (rejected — Track 1 evidence), then a properly-routed
`tasks/get` against a task she does not own (denied — Track 2 evidence). Both
`expected_detection_track_1` and `expected_detection_track_2` are `true`. Per Block 1/2, a
`HeaderMismatch`-rejected request never reaches authorization, so this is necessarily **two
distinct JSON-RPC requests** within one fixture — not one message tripping two tracks at once.
Included because the brief explicitly invited a combined scenario "if useful": it demonstrates
the tracks are additive within an attacker's session, not mutually exclusive alarms.

## Ground truth schema (`manifest.jsonl`)

Each row carries: `scenario_id`, `file`, `description`, `provenance` (`project_reference_harness`
for everything in this corpus — no scenario here is SDK-captured, consistent with
`docs/sdk-discrepancy.md`), `expected_security_outcome`, `expected_detection_track_1/2/3`,
`expected_confidence` (`high` | `low` | `not_applicable`), `violated_invariant` (a direct
pointer into `docs/state-invariants.md`/`docs/threat-model.md`), `required_evidence` (the exact
fields a later detection rule must key on), `cross_track_isolation`
(`track1_only`/`track2_only`/`track3_only`/`combined`/`null`), `experimental` (boolean), and
`notes`.

## What this corpus does not claim

- **No novelty claim for Track 2.** The underlying cross-principal/stolen-task-ID risk class is
  already documented in SEP-2663 itself and in prior MCP Tasks security discussion (Block 1
  §10). A7–A10 operationalize that known risk into testable telemetry; they do not claim to
  discover it.
- **No claim that current SDKs exhibit these behaviors live.** Every fixture here is
  harness-generated per `docs/sdk-discrepancy.md`'s verified findings about the current
  official SDK lines. A-EXP1 in particular is explicitly experimental for this reason.
- **No implication that ordinary drifted notifications carry protected resource contents.**
  A12/A13/A14 use `notifications/resources/updated`, which carries only a URI (Block 1 §11);
  only A-EXP1 (experimental) explores the content-inlining hypothesis, and does so labeled as
  such.
